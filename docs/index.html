Problem

Weekly status reports are manual, and risks get missed

A project manager writes a status report every week by reading the Jira board: a summary, a RAG status, the top risks and the decisions needed. Overdue tickets, issues that have gone quiet and high-priority work with no owner are easy to overlook in a list of dozens of rows.

Goal
A script that flags risks from a Jira export, plus a Claude prompt that writes the report.
Risk rules
Overdue, stale (no update for 7+ days), unassigned high priority.
Report format
Summary, RAG status, progress, top risks with issue keys, decisions needed.
Out of scope
Web app, Claude API, meeting notes.
Approach

Rules decide the facts. The model only writes.

Python applies exact rules, so the same input always gives the same risks. Claude is good at writing but can invent details, so it never decides what is a risk. It receives a small facts file and turns it into a readable report.

Risk rules

Applied to open issues only. Jira's Status Category decides what is finished; without it, Done, Closed and Resolved count as finished.

Prompt design

Four parts, saved as project instructions

The instructions live in a Claude Project, so every report follows the same rules without retyping them. Each part has one job.

Role and input

Defines the task and the only source of information.
You write weekly project status reports for a project manager.
I will paste a facts.json file produced by a script that checks a Jira export.

Grounding rules

Every statement must trace back to the facts file.
- Use ONLY the facts in the JSON. Do not add issues, numbers, names or causes that are not in it.
- Every risk you mention must include its issue key, e.g. ONB-118.
- If something a section needs is not in the facts, write "No data".

Fixed decisions

Judgement calls are made in the prompt, not by the model.
- RAG status: Red if there are 8 or more risks, Amber if 3 to 7, Green if 0 to 2. State the rule you applied.
- Do not guess causes, blockers, or what an issue is waiting for.
- Do not name the project, people or teams. None of them are in the facts.
- Do not calculate percentages or any new numbers. Use only the counts given.
- Title the report "Status report - <report_date>".

Output format

A fixed structure makes each report quick to review and easy to compare week to week.
Under 250 words, exactly these five numbered headings:
1. Summary: 2 sentences.
2. RAG status: colour + one-line reason.
3. Progress: done vs open counts.
4. Top risks: at most 5, grouped by rule, each with issue key and reason.
   Order: Overdue (most days late first), Unassigned high priority, Stale.
   Remaining issue keys listed on one "Also flagged:" line.
5. Decisions needed: one line per risk group, follow-ups by role, never by name.
Report accuracy

Controlling invented facts

Three controls work together. The model sees limited input, has fewer decisions to make, and every output is reviewed against the source.

01Limited input

Claude receives facts.json, never the raw export. The file contains no people's names, so any name in a report is an invented fact by definition.

02Rules in the prompt

The RAG threshold, the order of the top five risks and the banned content (causes, names, new numbers) are fixed in the instructions.

03Line-by-line review

Each issue key, count and reason is compared with facts.json. Results are logged in a review sheet, and the facts behind each report are saved with it.

Input validation

Making it work on real Jira exports

Real exports differ from test data in file format, column names and workflow statuses. The script checks its input before any rule runs. Problems that would make the risks wrong stop the run with a clear message; smaller problems are reported as warnings.

Use in practice

Where it fits in a delivery team

Weekly status reporting

Export the sprint from Jira, run one command with the report date, and paste facts.json into the Claude Project. The report has the same five sections every week.

python mvp.py sprint_export.xlsx 2026-10-16

Risk follow-up

Every overdue, stale or unowned issue is listed with its issue key and a one-line reason, so it can be opened in Jira and assigned an action.

Different Jira setups

Accepts CSV or Excel, matches column names flexibly and reads custom workflows through Status Category. The stale limit, high priorities and finished statuses are settings at the top of the script.

Reviewable AI output

The facts behind each report are saved with it, and every sentence can be traced to an issue key in that file. A reviewer can verify a report without trusting the model.

Scope
Three risk rules. Detection accuracy measured on two synthetic sprints; input handling tested on a real Jira export. Real company data is not stored in the repository.
