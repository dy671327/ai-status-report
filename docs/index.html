The problem

Status reports are slow to write by hand

Every week a project manager reads through the Jira board and writes a status report manually: summary, RAG status, top risks and decisions needed.

Risks buried in Jira get missed

An overdue ticket, an issue nobody has touched for a week, or a high-priority item with no owner can sit unnoticed among dozens of rows.

Goal from the project charter

A script that flags risks from a Jira CSV, plus a Claude prompt that writes the report.

IN SCOPE
  • 3 risk rules: overdue, stale, unassigned high priority
  • Synthetic test data
  • Claude Project prompt
  • Timing test
SUCCESS CRITERIA
  • Catches 10 of 10 planted risks
  • Zero invented facts in 3 reports
  • Time measured before and after

Why Python finds the risks

Python is reliable at checking rules: same input, same answer, every time. Each rule is one line of logic that can be explained and tested.

Why Claude only writes

Claude is good at writing but can invent things. So it never decides what the risks are. It only explains the facts it is given, in clear English.

The three risk rules

Applied only to open issues. Done, Closed and Resolved count as finished.

Prompt structure

Saved as project instructions in a Claude Project, so every weekly report follows the same rules and format without retyping. The prompt has four parts:

1. Role

You write weekly project status reports for a project manager.
I will paste a facts.json file produced by a script that checks a Jira export.
Tells Claude its job and where the input comes from.

2. Grounding rules

- Use ONLY the facts in the JSON. Do not add issues, numbers, names or causes that are not in it.
- Every risk you mention must include its issue key, e.g. ONB-118.
- If something a section needs is not in the facts, write "No data".
Every statement must be traceable to an issue key in facts.json.

3. Fixed decisions

- RAG status: Red if there are 8 or more risks, Amber if 3 to 7, Green if 0 to 2. State the rule you applied.
- Do not guess causes, blockers, or what an issue is waiting for. Describe each risk only with its reason from the JSON.
- Do not name the project, people or teams. None of them are in the facts.
- Do not calculate percentages or any new numbers. Use only the counts given.
- Title the report "Status report - <report_date>".
Judgement calls are written into the prompt as rules, so Claude doesn't make them itself.

4. Output format

Format (under 250 words). Use exactly these five numbered headings, in this order, and always include all five:
1. Summary: 2 sentences.
2. RAG status: colour + one-line reason.
3. Progress: done vs open counts.
4. Top risks: at most 5, grouped by rule, each with issue key and reason. Pick them in this order:
   Overdue (most days late first), then Unassigned high priority, then Stale (most days first).
   If there are more than 5 risks, end with one line "Also flagged:" listing the remaining issue keys.
5. Decisions needed: one line per risk group saying what the PM should decide or who to follow up with
   (by role, e.g. "the issue owner", never by name).
A fixed structure makes every report quick to check and comparable week to week.

How invented facts were tackled

1. Limit what the AI sees

Claude never reads the raw CSV, only facts.json. It contains no names, so any name in a report is an invented fact by definition.

2. Turn judgement into rules

The RAG colour, which 5 risks come first, and what is forbidden (causes, names, new numbers) are all fixed in the prompt.

3. Check every line

Each issue key, number and reason is compared with facts.json. Results are logged in pm/report_checks.csv.

What actually happened with report 1 (16 Oct facts)

Draft 1
3 invented

17 claims, 0 wrong. Invented a project name, said ONB-118 was "waiting on a reviewer", and said stale issues "may be blocked or abandoned". No RAG section; listed 10 risks instead of 5.

Fix: added rules banning causes, names and new numbers; fixed the headings and top-5 order.

Draft 2
5 invented, 1 wrong

Ignored nearly every rule. The project instructions were not being applied to the chat.

Fix: pasted the instructions and facts.json together in one message.

Final
0 invented, 0 wrong

22 claims checked. Correct title and five headings, RAG Red with the rule stated, top 5 in the set order, the other 5 under "Also flagged", follow-ups by role only.

Lessons: every gap in the instructions is a place where AI fills in its own judgement; checking finds the gaps and rules close them. And a prompt only works if it actually reaches the model.

How it can be used in industry

Weekly reporting for PMs and PMOs

Teams that track work in Jira can export a CSV each week, run one command, and get a report with a summary, RAG status, top risks with issue keys and decisions needed, in the same format every time.

python mvp.py data/sample_jira.csv 2026-10-16

Risks surfaced, not buried

Overdue work, issues nobody has updated in a week, and high-priority items with no owner are pulled out automatically, each with a reason and an issue key the PM can follow up on.

Adjustable to a team's rules

The stale limit, which priorities count as high, and which statuses count as done (Done, Closed, Resolved) are settings at the top of the script, changed in one place.

AI output that can be trusted and audited

Because rules decide the facts and AI only writes the words, every sentence in a report can be traced back to facts.json, and the facts used for each report are saved alongside it.

Current limitations

  • Tested on synthetic data only, no real company data
  • 3 rules: overdue, stale, unassigned high priority
  • Out of scope for the MVP: web app, Claude API, meeting notes
  • Still to do: reports 2 and 3, a fresh unseen dataset, and before/after timing
